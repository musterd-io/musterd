# 03 — Server (`@musterd/server`)

> **Living document.** This is the initial direction, not gospel. It will evolve. If you (the executing agent) find an error, contradiction, or better approach during implementation: (1) do not silently deviate — record the issue and your proposed change in `docs/decisions/NNN-<slug>.md` (a short ADR: context, problem, decision, consequences), (2) make the smallest correct change, (3) update the affected doc in the same commit. Docs and code must never disagree at the end of a commit.

The daemon. SQLite store + WebSocket + HTTP API + presence tracker + inbox delivery. Depends only on `@musterd/protocol`.

## Stack

- Runtime: Node ≥ 22 (repo-wide `engines`; native TypeScript execution is relied on by repo tooling).
- HTTP + WS: a single Node `http.Server`; HTTP routes handled directly (no framework needed — small surface), WS via the `ws` package upgraded on `/ws`. (If a router helps, `hono` is acceptable — record the choice in an ADR if you add a dep.)
- DB: `better-sqlite3` (synchronous).
- Validation: `@musterd/protocol` zod schemas at every boundary.
- IDs: `ulid`. Hashing: Node `crypto` (`sha256`).

## Startup sequence (`createServer().listen()`)

1. Load config (`config.ts`): port `MUSTERD_PORT||4849`, host `MUSTERD_HOST||127.0.0.1`, db `MUSTERD_DB||~/.musterd/musterd.db` (or injected `db` for tests), plus TLS (`MUSTERD_TLS_CERT`/`MUSTERD_TLS_KEY`), `--insecure-trust-proxy`, the WS upgrade allowlists (`MUSTERD_ALLOWED_HOSTS`/`MUSTERD_ALLOWED_ORIGINS`), and the env-tunable timeouts (ADR 040).
   - **Secured-bind guard (ADR 040).** `createServer` calls `assertBindSecurity` immediately, before opening the db: it **refuses** a non-loopback host (anything outside `localhost`/`::1`/`127.0.0.0/8`) unless native TLS is configured _or_ `--insecure-trust-proxy` is set — a helpful refusal naming the host and the three ways forward. With TLS the daemon is an `https`/`wss` server (`createHttpsServer`); else plaintext `http`/`ws`. Loopback default is unchanged.
   - **Roster roots (ADR 058).** Config also resolves the durable seat-roster roots via `resolveRosterRoots` — the union of `MUSTERD_TEAMS_DIR` (comma/colon-separated) and the `rosterHome` registry in `~/.musterd/config.json` (written by `musterd team export`). Watch debounce is `RECONCILE_DEBOUNCE_MS = 250`. An explicit `opts.rosterRoots` (tests) overrides; `[]` disables reconcile.
2. `openDb()` → set `WAL` + `foreign_keys` → `runMigrations()` (to the latest schema version). On **Cloud** (§Cloud mode) both stores are `pgDriver` instead, nothing migrates, and `listen()` refuses a database not at exactly this build's version before it binds; it then starts only the database loops (`cloud/loops.ts`).
3. Build the `ctx` bundle (`db`, `hub`, `config`, `rosterRoots`); the `hub` starts as an empty connection registry.
4. Mount HTTP routes (`transport/http.ts`) and WS upgrade handler (`transport/ws.ts`) on one `http.Server`.
5. **Boot reconcile (ADR 058).** When roster roots exist, `reconcileAll(db, ctx.rosterRoots)` projects the durable `.musterd/` files into the db before serving (logged `reconcile_boot`) — idempotent, so the roster the first request sees matches git.
6. `listen(port, host)` → resolve with bound address. Then start the presence `reaper` interval and, when roster roots exist, the debounced roster `watcher` (a change → full `reconcileAll`). The WS upgrade handler runs the pure `checkUpgrade` Origin/Host gate (ADR 040) on every upgrade — a present `Origin` (a browser; CLI/MCP clients send none) must be allowlisted, and the `Host` must be loopback, the bound host, or allowlisted — rejecting with `403` otherwise to blunt cross-site / DNS-rebinding abuse.
7. `reload()` (wired to **SIGHUP** by the daemon bin): re-resolve roster roots, `reconcileAll`, and re-point the watcher — so a team exported after boot is picked up without a restart.
8. `close()`: stop reaper + watcher, close all WS conns, close http server, `db.close()`.

## Presence heartbeat rules (load-bearing constants)

> These four constants are the **defaults**; each is **env-overridable** for WAN-tuned teams (ADR 040) via `MUSTERD_HEARTBEAT_INTERVAL_MS`, `MUSTERD_PRESENCE_TIMEOUT_MS`, `MUSTERD_REAPER_INTERVAL_MS`, `MUSTERD_RECLAIM_GRACE_MS` (positive-integer ms, zod-validated). The same-workspace reap grace (ADR 092) is likewise `MUSTERD_SUPERSEDE_GRACE_MS` (default 5s); observer idle TTL / concurrent idle cap are `MUSTERD_OBSERVER_TTL_MS` (ADR 064, default 24h) and `MUSTERD_OBSERVER_IDLE_CAP` (ADR 196, default 8). Out of the box the values below are unchanged. The reaper and the WS close path read them from `ctx.config`, so an override takes effect everywhere; the newest-wins self-heal (ADR 017) is tested at WAN-like timing.

- `HEARTBEAT_INTERVAL_MS = 15_000` — clients send `heartbeat` (or any frame) at this cadence.
- `PRESENCE_TIMEOUT_MS = 45_000` — 3 missed intervals. A presence row with `now - last_seen_at > timeout` is stale.
- Reaper runs every `15_000ms`: deletes stale rows, and for each removed row emits a `presence` offline event to the team **iff** that member now has zero live presences.
- On clean WS close: `detach()` immediately + emit offline (if last presence). Don't wait for the reaper.
- `status` transitions: a member is `online` if any presence row is fresh; `away` is only set explicitly by a client (`heartbeat` with `{status:'away'}` or HTTP presence ping) — the server never invents `away`. No fresh presence ⇒ `offline`.

## Single-active + reclaim grace (kind-scoped — v0.2 ADR 010, newest-wins ADR 017, kind-scope ADR 042)

- **Single-active is kind-scoped (ADR 042).** It binds **agent** seats; **human** seats fan out.
  - **Agents — one live Presence, newest wins.** On a WS `claim` for an _agent_ Member that already holds a live Presence, the handler **displaces** the existing session: it sends each old connection a `superseded` error frame, force-closes it (`Connection.close`), evicts it from the hub, clears the member's presence rows, then attaches the new Presence. The newest session is the one live occupant. (ADR 017 replaced ADR 010's _refuse with `member_busy`_ — refusing locked a Member out of its own seat after a reload/orphaned adapter; the dogfood deadlock.) The displaced adapter treats `superseded` as terminal and does not reconnect, so there's no ping-pong and orphans self-heal.
    - **Displacement is workspace-scoped (ADR 068), with a durability gate (ADR 092), and the workspace is the WORK TREE, not the label (ADR 368).** The claim frame's `workspace_key` is held on the live hub `Connection` (`workspaceKey`), **not** persisted on the presence row — it answers "is this claim my own session" for connections the hub can still see, which is the only question displacement asks; the roster keeps showing the ADR 014 label. `sameWorkspace(old, frame)` compares `frame.workspace_key` with the incumbent Connection's `workspaceKey` when **both** are non-null, and falls back to exact `workspace` **label** equality when either is null (an un-rebuilt client dist ⇒ exactly the pre-ADR-368 behaviour; the mixed-version window is a rebuild, not a release). The label may not be the key: it is ADR 014's where-on-attach seed, qualified with the git branch, so a branch switch or a detached HEAD renames it under the session holding it — the seat's own re-attach then compared unequal, took the cross-workspace path, and evicted the live session with `claim.superseded {same_workspace:false, via:'ws'}`, leaving the dormant orphan ADR 092 exists to reap (measured 2026-09-02). A claim from a _different_ workspace displaces immediately (a genuinely different session). A _same_-workspace claim does **not** supersede at claim time — a transient ~90s health-check probe spawns from the same workspace and must not flap the seat. Instead, once the successor proves durable (still attached after `supersedeGraceMs`, default 5s), it **reaps** the same-workspace predecessor(s) it found: sends them `superseded` with `same_workspace:true`, closes and clears them. A probe disconnects before the grace, so the reap timer finds the successor gone (`hub.getConn`) and keeps the incumbent. The reap arms a warn-level `claim.duplicate_workspace` audit row at schedule time (drift signal); the successor's own close cancels its pending reap. This is the fix for the orphaned-adapter war (#118) without regressing ADR 068's anti-flap. **A reload keeps its surface (ADR 489):** only a predecessor whose `Connection.surface` equals the successor's declared surface is collected for the reap (`isReloadOf`, `hub.ts`; also on the admin-approve path). A same-workspace successor on a different surface — the seat's own `musterd inbox --wait` (`cli`) beside its adapter (`claude-code`) — coexists: neither reaped nor displaced, and no `claim.duplicate_workspace` row is written.
    - **A wake never displaces an attended session (ADR 444).** Before any authorization step, an agent-seat claim carrying `provenance: 'wake'` is refused `claim_conflict` (WS `refused` frame; HTTP 409) when any of the seat's live hub connections backs a presence row whose provenance is not `wake` (`heldByAttendedSession`, `store/presence.ts`). No grant is consumed, nothing is displaced, and `claim.refused {code:'claim_conflict', reason:'attended_session'}` is audited. The converse is unchanged: an attended claim still displaces a wake, and wake-to-wake stays newest-wins. The host reads the refused wake as another session's occupancy at the end of its verify window and defers it (ADR 238).
  - **Humans — fan out.** A `hello` for a _human_ Member skips the displace loop and the `clearMemberPresence` clear: it attaches an _additional_ Presence and `hub.add`s the new connection alongside any existing ones, so a person can watch on a phone while acting on a laptop. `hub.deliver` already pushes to **all** of a member's connections and `broadcastTeam` iterates every connection, so a directed `deliver` and a `@team` broadcast both reach every human surface; the durable inbox cursor dedupes (at-least-once). The roster collapses the N Presences to one member row via `listPresence` (the `presences[]` array carries the surfaces). The single-active rule exists to stop _parallel autonomous minds_ wearing one agent identity — an agent hazard, not a human one (`docs/design/deployment-topology.md` §7).
- **Reclaim grace (both kinds).** On detach (clean close or reap), the _that_ Presence is held for `PRESENCE_TIMEOUT_MS` (45s) via a `held_until` marker (presence schema v2) so the _same_ Member can rejoin without being refused. The reaper sweeps expired holds **per Presence**, and a Member only goes offline when its **last** live Presence drops. This makes a flaky reconnect or a quick restart seamless while still freeing the seat promptly.

## Roster activity (v0.2)

- `listPresence`/roster `summarize` resolve a coarse `activity` per Member by the **two-clocks rule** (`store/activity.ts` `resolveActivity`): the liveness clock (fresh presence?) decides `offline` vs present; the status clock (latest `status_update`, via `latestStatusUpdates` — every member's in one statement, the same per-member `ORDER BY ts DESC, id DESC LIMIT 1` over `idx_messages_from_act_ts`; prefers `meta.state`, falls back to body) decides `idle` (ADR 140; was `online`) vs `working`. A third signal, **steering** (ADR 155 Inc 1), overrides both: a human named as the `driver` of a _live_ agent seat (`listLiveDrivers`) reads `working` and present without their own heartbeat — derived here at read time, no synthetic presence row — so a driving human stops reading offline on the roster (the driver-copresence fix). The backing summary is returned as `state`, with `last_status_at` driving the CLI's `· <age>` staleness suffix. These are **additive** roster fields; a v0.1 reader ignoring them still conforms. A roster read costs the same number of statements at any team size (lane 01M3ZCTQK9, `transport/roster-statements.test.ts`): `listPresence` reads every member's live presences in one statement and groups them, and the status clock is one statement — before, each was a query per member, about 300 statements per read at 151 members, every one its own transaction on Postgres.
- `summarize` also sets **`posture`** (ADR 138) and **`offline_reason`** (ADR 141) — composed chip reads from activity ∩ availability, with sticky `members.last_offline_reason` + reclaimable/off_hours overlays when offline.
- `summarize` also sets **`reclaimable`** per Member (ADR 105) from `listReclaimableMemberIds` (`store/presence.ts`) — a seat whose reclaim hold is still in the future (`held_until > now`). This is the one _positive_ read of held rows (every other query filters them out); the seat still reads `presence: 'offline'` (grace stays hidden from display), but the flag lets the client-side clobber guard (ADR 066) treat a held-within-grace reservation as occupied rather than a vacancy. Additive; older readers ignore it.

## Availability (v0.2 — ADR 044)

- **`POST /teams/:slug/availability`** (authed via `authMember`): the caller sets **their own** seat's availability axis (SPEC A.6 Axis 2). Body `{ status: available|away|dnd, until? }`; `until` (ms epoch) rides only `away` (the `away_until` encoding) — the handler drops a stray `until` from `available`/`dnd` so the stored shape can't lie. Persisted by `store/members.ts` `setAvailability(db, memberId, availability|null)` into the **existing `members.availability` TEXT column** (JSON-encoded) — **no migration**. `rows.ts` `toMember` parses it back through `AvailabilitySchema` defensively (a malformed/legacy blob degrades to `null` = implicit-available). Returns the updated member summary.
- **Never inferred, self-only.** Only the member's own authed call sets it; no other seat or heuristic does (contrast presence/activity, which are derived). The roster `summarize` already carries `availability` via `toMember`, so it surfaces with no extra plumbing. The notify loop reads it back **client-side** to tier deliveries (away holds all but `urgent`; dnd passes directed + `urgent`); the server only stores + exposes. The v0.3 governed superset — `off_hours`, schedule enforcement, the `can_*` capability gating who may set/flag — is the named seam, not built here.

## The wall (ADR 442)

A seat reaches no session outside the seat set. The daemon's share of that is small, and all of it is here:

- **No `delivery_hint`.** `routeEnvelope`'s ack carries none for any recipient kind — the seat↔seat relay (ADR 167 increment 2) and its `nudge.decision` audit row are gone. The `DeliveryHint` type stays in `@musterd/protocol` so an older daemon's ack still parses; nothing acts on one.
- **`gate.session_denied`.** `POST /teams/:slug/actor` with kind `session-denied` writes one audit row per refused call: `result: deny`, `target: null`, detail `{tool, harness?}` — no body, no session id, no credential. The row records a decision the client already made (the CLI gate refuses locally, before any round trip — `04-cli.md`); it is not the decision, and a daemon outage loses only the row.
- **Lines are pointers.** Every interrupt, wake and nudge line the daemon composes names its team (`musterd [<team>]:`) and says to read it as yourself; it never carries a body. A seat acts only on what its own authenticated read of the named act returns.
- **What this does and does not protect:** the wall stops model mistakes — cross-session and cross-identity. It is not a boundary against a hostile process under the same OS user; that is credential custody (`docs/design/security.md`).

## The doorbell (ADR 443)

Something addressed to a human rings them through surfaces musterd owns, never a harness session.

- **What rings** — `ringTargets` (protocol): a directed `ask`/`request_help`/`handoff` to a human rings that human; any other `ask` rings the admin humans; a `lane_review` ask only when directed to a human. `routeEnvelope` calls `notify/doorbell.ts` `ringDoorbell` after persist + deliver, and it never throws into the send.
- **The record** — structured fields only (`team, from, act, species?, tier?, act_id, deadline_ms?, answer_path`), strict, no body. `doorbell_rings` (migration v70) stores one row per rung human: `held` → `queued` (waiting for a host) → `done`.
- **Routing** — `getDoorbellPolicy` (team allow-list, defaults and URLs; ADR 149's `ask_slack_webhook` read through as the team slack URL) → `resolveRoute` with the human's own `members.doorbell_prefs`. A self-set `away`/`dnd` holds (`holdsRing`); `blocking` pierces `dnd`; `off_hours` never holds. `flushHeldRings` runs on the availability POST and `flushLapsedHolds` on the reaper tick (a lapsed `until`). At flush, an answered or resolved act is dropped.
- **Sinks** — `slack` and `webhook` POST from the daemon: one attempt, detached, resolve-and-pin with no redirect followed (`notify/pinnedPost.ts`), one POST per URL per act, ADR 155 present-quiet at raise. `os` waits for the host (`POST /doorbell/rings`, then `/doorbell/rings/:id/surfaced`). `live` needs nothing from the daemon. Every attempt audits `doorbell.surfaced {surface, ok, status?}`, never a URL or a body.
- **Privacy** — `/members/me/doorbell` is self-only. An admin's `/members/:name/doorbell` goes through `maskPrefs`. Every sink URL must be `https` to a public host (`publicHttpsUrlProblem`), checked at `PUT` and at `POST /policy`.
- **SSRF, closed (2026-10-02)** — the `PUT`-time check reads the literal host and resolves nothing, so a public name pointing at a private address passed it. Every sink POST now resolves the name itself, refuses the send if any answer is loopback, link-local, private or otherwise not global unicast, and pins the TLS connection to the address it checked (`pinnedPost.ts`, the CIMD resolver's address policy). The `PUT` check stays as the early, user-facing refusal.
- **What this does and does not protect:** see [SPEC §3](../../SPEC.md#3-collaboration-acts) (the doorbell) — one home for that fact.

## Telemetry (v0.2 — ADR 015, off by default)

- `telemetry.ts` adds minimal OpenTelemetry (observability.md §4). `routeEnvelope` is wrapped in a `musterd.envelope.process` span with `musterd.*` attributes (team/act/from/to.kind/envelope.id/thread + `otel.traceparent` from `meta.otel`, ADR 011; ADR 101 adds `musterd.model` + `musterd.model.family` from the sender's attested occupancy, beside the `musterd.from.id` normalized-seat dimension) — **never the body**. Metrics: `musterd.envelopes` (counter), `musterd.delivery.latency` (histogram, by team), `musterd.errors` (counter; recorded at the transport boundary in `http.ts`/`ws.ts`), `musterd.presence.churn` (counter), and the observable gauges sampled on collection — `musterd.presence.active` (live presences by surface), `musterd.inbox.lag` (age of the slowest unread inbox), and `musterd.insight.diversity_flags` (live model-diversity flags by team, ADR 101), plus `musterd.trace.ingest` (trace events stored from the hook tap, by harness and kind — ADR 445), backed by `store/metrics.ts`/`store/mast.ts` and registered via `registerRuntimeGauges` in `listen()` (only when telemetry is enabled). ADR 082 added the coordination metrics `musterd.coordination.loop_latency` (accept/decline/resolve vs the act they close, by team and the closer's model family), `musterd.coordination.seen_latency` (read-side latency by team), and `musterd.coordination.open_loops` (unanswered request_help/handoff, sampled by team via `countOpenLoopsByTeam` in `store/messages.ts`). The opt-in `musterd.agent.tokens` counter remains self-reported via `meta.usage`, now by team, member/direction, and model family.
- **HTTP request log (ADR 082):** the `createServer` handler emits a structured `http_request` line per request — `method`/`path`/`status`/`ms`, info 2xx/3xx, warn 4xx, error 5xx — path only (no query/headers), and the path passed through `redactPath` (`log.ts`) first — every segment under an `mcp` segment and any credential-shaped segment becomes `[redacted]`, so a remote MCP connector URL (`/mcp/<token>`) never reaches `daemon.log`; the unmatched-route 404 body echoes the same redacted path. `/health` polls skipped. This is the HTTP layer `daemon.log` previously lacked (finding 001). A 5xx line also says why (lane 01M3ZPM3FE): `err_class`, `sqlstate` when Postgres raised it (the pg driver nests the server's error as `cause`), and `err` — the message on one line, credential-shaped text redacted (`redactCredentialText`), cut to 300 characters; the handler notes it (`noteRequestFailure`, REST `sendError` and both `/mcp` error paths) and the logger reads it when the response finishes. Before this, the 2026-10-03 Cloud load run's 261 × 500 left `status: 500` and nothing else.
- **Off unless** a standard OTLP endpoint env is set (`OTEL_EXPORTER_OTLP_ENDPOINT` etc.); never when `OTEL_SDK_DISABLED=true`. No phone-home. `createServer().listen()` calls `startTelemetry()` (dynamic-imports the SDK only when enabled); `close()` flushes it. When off, the `@opentelemetry/api` calls are no-ops.

## The trace store (ADR 445)

- **A second database file.** `db/traceDb.ts` opens `trace.db` in the coordination store's directory (`MUSTERD_TRACE_DB` overrides; `:memory:` follows `:memory:`, and an injected test `db` gets an in-memory trace store so no test writes a real file). It has its own `schema_meta` and its own forward-only ladder, run by the shared `runMigrations(db, ladder)`; `pnpm migrations:check` parses both ladders. Nothing joins across the two files at write time — `team_id` and the seat name are carried as text, and the join key to the coordination store is `(session_digest, tool_use_id)`, present in both. `/health` reports `trace_db`, `trace_schema` and `trace_db_bytes` (file + WAL; omitted for `:memory:`) beside `db` and `schema`.
- **One table, `trace_events`:** `(id, team_id, seat, session_digest, seq, ts, received_at, harness, kind, tool_name, tool_use_id, agent_id, parent_agent_id, duration_ms, outcome, detail, content, redactions, truncated)`, `UNIQUE (team_id, session_digest, seq)`. `detail` is bounded structural JSON (sizes, enums). `content` (the scrubbed fields as JSON), `redactions` (the hook's count plus the daemon's) and `truncated` are written only when the team's `trace.content` is `on` (increment 1b); otherwise a content part that arrived is dropped, never stored.
- **`POST /teams/:slug/trace/events`** — `{ events: TraceEvent[1..256] }` → `202 { accepted, content }` — `content` is the team's `trace.content` mode, which is how a tap learns it without a second round trip. Seat credential, **leaseless** (`authMember(…, {leaseless:true})`, the second such route after `/workspace/repair`): a SessionStart hook posts before the session has joined, and the rows are the seat's own record of its own session. Presence-neutral (no `authTouch`) — a hook rides every tool call and must never flip the roster. The seat is the caller; the body has no field for it. Parsed at the boundary through `TraceEventBatchSchema` (an over-bound content part is a 400, no partial write). Counter: `musterd.trace.ingest` by harness and kind.
- **What is captured today (Claude Code):** `SessionStart`/`SessionEnd` from the capture hook, `PreToolUse` from the gate (on the tools it is registered for), `PostToolUse` from the interrupt probe (every tool), and `UserPromptSubmit`/`PostToolUseFailure`/`Stop`/`SubagentStart`/`SubagentStop`/`PreCompact` from the standalone `musterd trace hook`. **Codex:** `SessionStart`/`SessionEnd`/`PostToolUse` from `codex-hook start|end|post-tool-use`. **Cursor:** `PreToolUse` from the gate; `sessionStart`/`postToolUse`/`afterShellExecution`/`afterMCPExecution` from `session observe` (all three post-call events record as `PostToolUse`, the source name in `detail.hook_event`); `SessionEnd` from `session end`. **Grok:** `PreToolUse` from the gate and `SessionStart`/`SessionEnd` from capture; its `Stop` and interrupt-probe events are not tapped until its hook lines name themselves (ADR 445 Consequences, 2026-09-25). The gate and each harness's interrupt probe also post a `HookOutcome` (`detail.hook`, `exit_code`, `duration_ms` = the hook process's life, `decision`/`raised`) in the same batch as the event they observed. **Content (1b):** when the tap's cached mode is `on` and the daemon is loopback, the observed event carries its scrubbed content part (a `HookOutcome` never does). **Rail R2 (increment 2):** the transcript tail (`cli trace/tail.ts`, riding the Claude `Stop`/`SessionEnd` and Codex `post-tool-use`/`end` hook processes) posts `reasoning`/`assistant_text`/`usage` rows keyed to the same digest, joined to R1 by `tool_use_id`; an unrecognised transcript record arrives as `unknown`, and a downgrade marker (`unknown` + `detail.downgraded`) makes the ingest route write a `trace.downgraded` audit row in the coordination store.
- **The content lifecycle (increment 3a).** `startTraceContentPrune` runs `pruneTraceContent` a minute after boot and hourly after that: rows whose `content` is older than 30 days (`received_at`) get `content = NULL` and `content_pruned_at = now`, in 2,000-row transactions, at most 25 per pass; structural columns are never touched. On an archiving machine — one where `pnpm corpus:snapshot` has stamped `schema_meta.content_captured_through` — a row is pruned only once it is also strictly below that watermark, so the prune never destroys the only copy. A machine that never archived gets the plain 30-day bound. The scan rides the partial index `idx_trace_events_content_age`. Replication of structural rows (§3's `record` kind) is not built: it is lane `01M3DG52YV` (increment 3b), pending its own ADR on the cost to `musterd.db`.
- **Replication (ADR 453).** `POST /teams/:slug/sync/trace` — `{ rows: SyncTraceRow[1..1000] }` → `200 { accepted, ignored, collided, refused: [{id, code}] }`. Machine credential (`msnode_`), the `/sync/push` refusal shape. The wire schema is structural-only by type: closed enums, counts, flags, 24-hex id digests, a per-kind closed `detail` table, `tool_name` in the harness namespace (or `other`), and the credential detector on every string field — a non-conforming batch is a 400 with nothing written (the hub REJECTS; only the pusher and local ingest normalize). Residence per row (ADR 360 applied outside the fold): a seat bound to another node refuses ONLY its row (listed in `refused`, not written, the batch goes on, the cursor advances past it); an unresolved seat (roster lag) or an unbound seat holds the whole batch with `409 { reason: 'unresolved_seat' | 'unbound_seat', seat }` — the trace surface never mints a binding; a service seat (ADR 232) is admitted from any node. No audit row on any refusal. Rows land in the hub's `trace.db` with `origin_node` set (trace ladder v3), never in `sync_log` or `audit`, and the hub forwards nothing. Counter `musterd.trace.replicated` by origin node and outcome; local ingest's normalizations count on `musterd.trace.normalized`.
- **`GET /teams/:slug/report`** — `200 Report` (`deriveReport`). Shared across viewers and derived off the event loop (`store/reportCache.ts`): one derivation per team serves every reader for 5 s; past that a reader gets the last report at once while one refresh runs, and past 60 s it waits for the fresh one. `generated_ts` is the derivation time, so a reader can always tell the age. A file-backed daemon derives in a worker thread on its own read-only WAL connection; an in-memory store derives inline, uncached. Cloud derives inline behind the same cache, under the requesting team's scoped handle so RLS holds; the service is keyed by the server's root store, because Postgres mints a team handle per request. Why: the 2026-09-28 demo-scale bench measured the synchronous 1-3 s derivation, polled by 50 viewers, at p95 13 s and dragging every route to p95 1-4 s (lane 01M3D4069F); the 2026-10-03 Cloud load run found the cache keyed per request — 1 346 full derivations in 22 minutes (lane 01M3ZCTQ77).
- **`GET /teams/:slug/report/trace?days=N`** (increment 4, behind `musterd report trace`) — `200 TraceReport` (`window_days`, `seats`, `coverage[]`, `tool_mix[]`, `lane_cost[]`, `unattributed`). Ordinary authenticated read (`authTouch`), ADR 128-scoped at the route: an admin's `seats` is the whole roster, anyone else's is their own name — filtered, never refused. `days` outside 1..90 falls back to 7.
- **`GET /teams/:slug/huddles/:id/trace`** (ADR 493, behind `musterd huddle show <id> --trace` and `/live`) — `200 HuddleTrace`: the huddle header, one row per seat in the room (how it was summoned, its wake joined by the act it answered, time-to-turn) and one ts-sorted event list (acts, wakes, structural tool calls, non-ok hook outcomes, session marks) over the window open → close (or now, capped at 2 h), at most 2,000 events. A Member in the room or an admin reads it; anyone else gets the same `404` as a missing huddle (ADR 128). Tool events are structure only — never `content` or `detail`.
- **`GET /teams/:slug/trace/seats/:name?limit=N`** (increment 4b, behind the `/live` roster's `trace` expander) — `200 { seat, events }`, newest first, `limit` 1..200 (default 50). Same ADR 128 scope as the session read; the store read (`listSeatTrace`) never selects the content column, so `content` is null on this wire whatever the team's `trace.content` says.
- **`GET /teams/:slug/trace/sessions/:digest`** (increment 2, behind `musterd trace show`) — `200 { events }`, seq-ordered, `detail`/`content` parsed back to objects, `content_pruned_at` carried so a reader can tell pruned from never captured. Ordinary authenticated read (`authTouch`), scoped per ADR 128: a seat gets its own rows; an `is_admin` seat gets any seat's; everything else filters to empty — "not yours" and "not there" are deliberately the same answer, so the route is no oracle for which digests exist.

## Seat memory (ADR 093)

- **A daemon-private, seat-scoped continuity blob.** `store/memory.ts` backs the `seat_memory` table (schema v13): one row per member (`member_id` PK/FK `ON DELETE CASCADE`), `headline`/`body`/`saved_at`, **last-write-wins** — no history, no versions. It is deliberately **not** in the git seat-file: this is live working state (presence's side of the ADR 058 durable/live line), and half-done context or a pasted secret must never land in repo history.
- **Store API:** `saveMemory(db, memberId, { headline, body })` upserts and stamps `saved_at = Date.now()`, enforcing `MEMORY_HEADLINE_MAX_CHARS` (120, by character count) and `MEMORY_BODY_MAX_BYTES` (8192, by **UTF-8 byte** length) — an oversize/empty input throws `bad_request` with the limit named. `getMemory` is the explicit body read; `memoryEnvelope` returns `{ headline, saved_at, size_bytes }` (`size_bytes` = `Buffer.byteLength(body)`) and **never the body** — it is what rides the occupied frame (ADR 093 §3). `clearMemory` deletes, returning whether a row existed (idempotent).
- **HTTP surface — seat-authenticated, own-seat only.** `PUT /teams/:slug/memory` (`{ headline, body? }` → `saveMemory` → `204`), `GET …/memory` (`200 { headline, body, saved_at }` or `404` when none; `?envelope=1` returns the headline-only envelope instead — the `musterd status` one-liner read, never the body), `DELETE …/memory` (`clearMemory` → `204`, idempotent). All three resolve the seat from the presented token (`authMember`), apply the banned-=-inert gate (`assertSeatCanRead` — a `disabled`/`banned`/`archived` seat can't touch memory either), and act on **the caller's own seat** — the URL carries no member name, so there is deliberately **no cross-seat read path** (team admins included, ADR 093 §4): an admin hitting `/memory` reads its _own_ note, never another's. The save schema (`MemorySaveBody`) shapes types only; the caps live in `saveMemory` so the 400 names the exact limit.
- **Envelope on occupy.** All five occupied-frame sites (WS; HTTP admin-approve, grant, credential self-authorize, and standing reseat) emit `memory: memoryEnvelope(db, member.id)` and the Member's Team Role `charter` when the role library declares one. A returning occupant's join frame carries the memory headline/age/size line plus authenticated Role context; the memory body travels only over the explicit `GET`.
- **Audit sizes-only.** `memory.save`/`memory.clear` audit actions carry `size_bytes`/`headline_len` in `detail`, never the headline or body text (hard rule 5).

## Shared Seeds (ADR 291/311/312, unreleased)

- **Authenticated Team reads.** `GET /teams/:slug/seeds` returns every Team Seed and
  `GET /teams/:slug/seeds/:id` returns one. Both use `authTouch`; an unauthenticated caller learns
  nothing about Seed existence. Responses are parsed through `SeedListSchema` / `SeedResultSchema`.
- **The stateless claim is workspace-scoped too (2026-09-04).** `POST /teams/:slug/claim` accepts
  `workspace` + `workspace_key` and records the label on the Presence. Displacement applies the same
  identity-first comparison as `ws.ts` (key when both sides carry one, label otherwise — ADR 368): a
  LIVE same-workspace session is spared (ADR 092), socketless rows are cleared because this claim
  succeeds them, and the `claim.superseded` audit reports the comparison it actually made. Until this
  landed the route attached `workspace: null` and evicted unconditionally, so `claim --detach` in a
  folder killed the session sitting in it.
- **…and it records provenance, on every branch that occupies (2026-09-05).** The repair above edited
  ONE of the route's three `attach` calls, so the credential self-authorize and dogfood re-seat
  branches kept hardcoding `workspace: null` — and the re-seat branch is the ordinary path for an
  agent re-claiming its own bound seat. The three literals are now one `claimAttachContext`, which
  cannot drift branch to branch. It also carries `provenance` (ADR 131 §6), which the body schema
  had never accepted at all: every row born here read `provenance: null` while every WS-claimed and
  every ambient-touched row carried a value — the two paths were exact opposites, the HTTP claim
  recording a workspace and no provenance, the ambient touch a provenance and no workspace. It costs
  a wake: the actuators judge `verified.provenance !== 'wake'` to tell their own spawned child from a
  stranger holding the seat. `provenance` is stamped on **agent** seats only, the same ADR 121 gate
  `ambientTouch` applies — a human shell must not be able to label its own occupancy `wake`.
- **Recorded intentions in the brief (ADR 373 inc 4).** `GET /teams/:slug/next` carries
  `up_next_seeds` (open Seeds, oldest first, compact: id/source/ref/summary/submitted_by) and
  `up_next_seeds_total`, projected by `openSeedsForBrief` and rendered above `up_next` on both
  surfaces.
- **Review promises (ADR 490).** An accepted typed review request — a root `request_help` to one
  Member carrying `meta.review`, answered by that Member's `accept` naming it in `meta.in_reply_to`
  — is a promise until a Team-addressed `resolve` lands on the request's thread. Derived from the
  Act ledger alone (`deriveReviewPromises`, `store/orientation.ts`): duplicate accepts collapse to
  the minimum `(ts, id)`, so every replica reports the same `accepted_at`. `GET /teams/:slug/next`
  carries `request_reviews` (owner), `requested_reviews` (requester) and `review_closures` — a
  non-owner close the owner has not read, judged against the inbox cursor on receipt order
  `(created_at, id)`, never the sender's `ts` — all three emitted even when empty (absence is an
  older daemon). `routeEnvelope` threads the accept onto the request id and refuses a
  Member-addressed `resolve` of a typed request. `GET /teams/:slug/review-promises?open=1` returns
  every open promise in the Team as `{request_id, requester, owner, accepted_at}` to any active
  Member — the `sweep` audit's read, with no prose and no artifact reference.
- **Parked lanes (ADR 466).** `parked` is a human's "kept, not now". `decideParkPatch`
  (`sync/claim.ts`, so the hub and the local path agree) admits a park only from a human, with a
  `park_reason`, from open/claimed/active/blocked; an unpark only from a human, to open or
  abandoned; and refuses any claim or handoff of a parked lane (409, naming who parked it and why).
  An agent that cannot proceed is pointed at `blocked`. The brief carries `parked_total`, never the
  lanes: `up_next` takes only `open`.
- **Closing asks what is left (ADR 487).** `decideFollowsUp` (`sync/claim.ts`, beside the park rules)
  refuses a submit or close by the lane's own closer when the lane declares itself one part of
  several (`leftoverSignal`: `N of M`, `N/M`, `increment N`, `phase N`, an id like `1A`) and neither
  the patch nor an earlier submit answered `follows_up` (`"none"` or lane ids). Every other close is
  unchanged; an acceptor is never asked. A named list must be existing lanes other than this one, an
  abandoned one carrying `abandon_reason`; goalless ones join the closing lane's goal inside the
  store's write transaction (so the hub path does it too), and a goalless lane naming goalless ones is
  refused with the `goal_id` / `team_goal_declare` repair. The acceptance ask carries the answer
  (`followsUpNotice`). S1 joins the signal: a lane carrying `unfinished_todos` (§5.2, written by the
  harness hook, last write wins) must answer too, and the ask lists the first five.
- **Repo capture (ADR 373 inc 2).** `POST /teams/:slug/seeds/repo` `{ref, body, captured_at?,
  lane_id?}` — a document-recorded intention as a Seed with `source: 'repo'`, idempotent on `ref`
  (201 created / 200 already held); `lane_id` links + promotes. Any seated Member.
- **Parsed lifecycle mutations.** `POST …/seeds/:id/claim`, `/clarification`, `/answer`, `/brief`,
  and `/promote` parse their bodies through the corresponding protocol schemas before calling the
  store. Only agents claim, only the active explorer asks or submits the final brief, only the
  submitting Member answers, and any Member may manually promote. Store transitions return the
  existing `forbidden`, `not_found`, or `conflict` errors.
- **Promotion activity.** The first automatic or manual promotion emits the normal Team
  `lane_open` message with `seed_id` and `brainstorm_recommended:true`. A retry returns the same linked
  Lane and emits no duplicate audit or activity row.
- **Content boundary.** Lifecycle audit rows carry only actor, Seed/Lane ids, state edges, result
  kind, and skipped-research metadata. Raw Seed bodies, Slack user ids, clarification/answer text,
  final briefs, and conclusions appear in neither audit details nor HTTP request logs.

## Inbox delivery semantics

- **At-least-once, cursor-based, no per-recipient copies.** The `messages` table is the single log. A member's inbox is a _query_ (see `listInbox`) filtered by their `inbox_cursors.last_read_ts`. "Mark read" advances the cursor.
- **Live + durable are the same data.** When a member is present, `hub.deliver` pushes the envelope to their socket immediately _and_ it's already persisted — so a reconnect re-reads anything missed via the cursor. A client may receive a message both live and on the next inbox fetch; clients dedupe by `envelope.id` (at-least-once contract; documented for CLI/MCP).
- Delivery to a recipient who is offline = nothing to push; the row sits in the log and surfaces on their next `inbox`/`reconnect`.
- `team`/`broadcast` deliver to all current members except the sender; each has an independent cursor.

## Auth

- **The tenant seam (cloud design §12.1; 1B):** a request's `ctx` becomes team-scoped exactly once — `handleHttp` resolves `/teams/:slug` as the operator (the one cross-tenant read a request makes) and shadows `ctx` with `teamCtx(rootCtx, team.id)` for every route under the prefix; `attachWsServer` does the same per connection once the claim frame names its team; `/oauth/:team` and `/mcp/:team` rebind after `requireTeamRedacted`. Everything above the prefix (`/health`, `POST /teams`, `/store/*`, `/node/enroll`, discovery) and everything the daemon does on its own behalf (the reaper, retention, the census, the sync loops, the sweeps — `index.ts` hands them `operatorCtx(ctx)`) runs as the operator. On SQLite every handle is the same object; on Postgres the `auth*` helpers below re-resolve the team through the scoped handle, which sees exactly that team, so a credential presented at the wrong team's host is `unauthorized` by row-level security, not by a comparison. `transport/tenancy-http.test.ts` pins it on PGlite.
- `authMember(token)`: `sha256(token)` → lookup `members.token_hash`. Returns the Member or throws `unauthorized`. WS `hello.token` and HTTP `Authorization: Bearer` both go through this. The `unauthorized` message points at the likely cause — a token minted against a _different_ db than this daemon serves (ADR 016).
- **Scoped bootstrap credentials (ADR 344/350/440):** HTTP and WS claim resolve an active, unexpired `mskey_` record by hash before target authorization. `claim_seat` and `claim_role` records fail closed unless the requested target matches the server-held target; `host` records cannot claim. Residency wake lease, progress, turn, and report routes accept a `host` record only when its target matches the request's host or the lease's stored host. Successful scoped claim/host authentication records `first_used_at`; legacy authentication never does. `POST /agent-bootstrap-migrations` derives Team and seat from a legacy key plus independent `msac_` proof and returns one shown-once successor without creating Presence. The server gives that successor a 90-day expiry; a retry replaces only an unused successor and starts a fresh 90-day window. The existing response and redacted admin inventory expose `expires_at`, never the secret or hash. Admin-only cutover GET/POST routes derive readiness from held agent Members, active residency hosts, and observed scoped use, then atomically revoke legacy records, clear the Team hash, stamp cutover, and append mandatory audit evidence. Mint/list/revoke remain admin-only and hashes never cross the transport.
- **Sponsor-scoped authority (ADR 463 §1):** a non-admin human in good standing with `can_create_agents` may mint a `claim_seat` credential, a seat grant, and residency — only for a live agent they sponsor (`authSponsor.ts`). A host key minted by a sponsor serves only that sponsor's agents, and a sponsored seat is bound to its sponsor's own key, never an admin host sharing the label. `POST /host/provisions` (claim) and `POST /host/provisions/:id/report` ride that host key (claimant only, once); `GET /host/provisions` is the read-only list. `POST /members/agents` returns `hosting: 'sponsor_host'` when it queued a provision, and `…/agents/:name/connect` refuses an agent already hosted (`connectRefusal`). Losing sponsor standing revokes the agent's residency, standing grant, OAuth chains and presence in one cascade (`sponsoredCascade.ts`).
- **Governed model authorization (ADR 411/414):** `governed_policies` is a server-owned, secret-free policy row and `governed_launch_authorizations` is separate from seat-claim `grants`. An active human Member may issue a one-shot `msla_` handoff only to an active agent Member with exactly one enrolled `seat_nodes` binding. The server stores only the handoff hash, consumes it with a guarded update when the matching Presence attaches, and evaluates node identity, launch state, live Presence, Lane/Act context, and model policy independently. The protocol parses orientation contexts for forward compatibility, but `/governed/authorize` refuses them with `denied_context_orientation` because no allowance record or issuance path exists yet. The route requires the enrolled node credential and a previously consumed launch; it returns a structured denial rather than throwing for an authorization refusal. `enforcement: off` is the default and no route in this increment activates `required`. Audit details contain IDs and policy/model metadata only — never credentials, prompt/response bodies, or provider payloads.

## Cloud mode (cloud design §5; increment 1C)

`MUSTERD_MODE=cloud` is one flag with a defined, tested set of effects; unset (or `self-hosted`)
changes nothing. It requires `MUSTERD_DATABASE_APP_URL`, `MUSTERD_DATABASE_OPERATOR_URL`, their
`MUSTERD_TRACE_DATABASE_*` twins, `MUSTERD_CONSOLE_JWKS_URL`, `MUSTERD_CONSOLE_AUDIENCE` and
`MUSTERD_CLOUD_HOST_SUFFIX`, and refuses to start without any of them (naming it, never its value).
Optional `MUSTERD_PG_POOL_SIZE` sets connections per pool (one pool per role per store; default 10).

1. **The store is Postgres.** Both stores are `pgDriver` over the configured URLs; no SQLite file is
   opened. Every statement runs in a stamped transaction; `BEGIN`, `SET LOCAL ROLE` and the tenant
   `set_config` go down as one round trip, so a bare statement costs three trips, not five. Migrations are **not** run on boot (§6): `listen()` refuses a database that is not at
   exactly this build's version — "schema newer than this build" / "schema older than this build".
   The migrate step is `scripts/cloud/migrate.mjs` (`migrateCloud`, as the owner, direct host).
2. **No loopback trust (§5.1).** `trustsLocalPeer` is false, and `trustProxy` is forced on. Seat
   provisioning and credential rotation take an admin credential; OAuth and remote MCP require the
   edge's `x-forwarded-proto: https`; the machine verbs (`/store/prune`, `/store/compact`,
   `/node/enroll`, the sign-in handoff and `local-identity`) answer **404** — on Cloud there is no
   machine a caller owns. `cloud/loopbackAudit.test.ts` (static) and `cloud/loopbackSweep.test.ts`
   (every former shortcut, from 127.0.0.1 with no credential) are the §8.3 test.
3. **Admin operations take a console token (§4.3/§5.2).** In increment 1 that is `POST /teams`:
   ES256, `aud` = `MUSTERD_CONSOLE_AUDIENCE`, ≤60 s, `jti` redeemed once across every server in
   `console_token_jti`. Refusals are 401 with the reason; an unreachable JWKS is 503 "console
   unreachable". The JWKS is the test issuer until increment 2's console. Team-level `is_admin`
   seats keep governing their own team with their own credential.
4. **Host isolation (§5.3).** A team lives at `<slug>.<MUSTERD_CLOUD_HOST_SUFFIX>`; a request whose
   path names another team (`/teams/:slug`, `/mcp/:slug`, `/oauth/:slug`, the OAuth discovery
   shapes) is **404**, and a WS claim for another team is `not_found`. Global routes (`/health`,
   `POST /teams`) answer on any host.
5. **`/health` is ok or one sentence (§5.5).** `200 {ok:true}` or `503 {ok:false, reason:"database
   unreachable"}` — no path, counts, or build. Any request that meets an unreachable store is a 503
   with the same sentence; recovery is automatic (the pool reconnects — and a dropped pooled
   connection is an `error` event the pool handles, never a process exit). No background path lets the
   outage exit the process either: a socket close, the reaper's tick, the same-workspace eviction
   timer and the expired-member sweep each log one stable line (`ws_cleanup_failed`,
   `reaper_tick_failed`, `ws_supersede_failed`, `expired_sweep_failed`) and carry on
   (`cloud/outage.test.ts`). The 2026-10-02 load test found all four exiting it (lane `01M3ZC3EXN`). The OAuth token endpoint
   answers the same outage `503 temporarily_unavailable` + `Retry-After`, never `invalid_grant` /
   `invalid_client` — RFC 6749 clients discard a refresh token or a registration on those. `/live`
   shows the sentence as a banner (`packages/web/src/live/serverHealth.ts`).
6. **Only the database loops run** (`cloud/loops.ts`): reaper, trace prune, trace coverage,
   expired-member and provision sweeps. Not the roster watcher, the footprint sampler, federation
   sync, audit retention (it archives to a local file first; Cloud retention arrives with the backup
   pipeline, §7), or seeds ingest (it fetches a relay URL a team admin sets, with no public-host
   check — on a fleet, an outbound request any customer could aim inside the platform).
7. **No team rows without a credential (§4.3).** The roster reads (`GET /teams/:slug`,
   `GET /teams/:slug/members`) answer an anonymous caller on a loopback daemon — the projection scopes
   itself to whoever asks, and anonymous there means "on this machine". On Cloud they require a
   credential for the team (`rosterViewer`), so the internet cannot list a team's members.

Rate limits and quotas (§5.4) are their own lane, not part of increment 1's acceptance.

## Diagnostics (ADR 016)

- On **Cloud**, `GET /health` is only `{ok:true}` or a 503 with one stable sentence (§Cloud mode); `/live` polls it for the outage banner, and stops polling once a self-hosted body answers.
- Self-hosted, `GET /health` → `{ ok, v, db, schema, connections }` — `db` is the served database path, `schema` the applied migration version, and **`connections`** (ADR 047) is a derived count of distinct members holding a _live_ presence **across all teams** in this db (`countLivePresences` mirrors the roster's live filter: fresh heartbeat, not a release hold). It's the signal the CLI's `service stop|restart` guard reads to refuse bouncing a shared daemon out from under a teammate; a bare count (not names) keeps this unauthenticated endpoint from becoming a cross-team member directory, and it's additive/back-compatible (no protocol bump). `musterd serve` prints the db path **and the effective host + scheme** (`ws://…` vs `wss://…`, plus a note when a TLS-terminating proxy is trusted) on startup and logs `host`/`scheme`/`db`/`schema` on `listening`; `RunningServer.dbPath` and `RunningServer.scheme` expose them (ADR 040 extends this posture so "what is this daemon exposing?" is answerable). This makes "which db is this daemon serving?" answerable, so a daemon accidentally serving the wrong db (reads as "everyone offline") is self-diagnosing.
- Team creation (`POST /teams`) needs no token on a self-hosted daemon; it mints the creator Member + token. On **Cloud** it needs a console token (§Cloud mode).
- A token authorizes acting **as that one Member in that one Team**. `forbidden` if the envelope `from`/`team` don't match the authenticated Member.

## Acceptance tests (gate before CLI work — see `06-testing.md`)

- DB opens, migrates to the latest schema version, PRAGMAs set.
- `POST /teams` → creates team + creator member + token; duplicate slug → `409 conflict`.
- `addMember` issues a token whose `sha256` matches stored `token_hash`; plaintext never stored.
- `routeEnvelope` persists + returns correct recipients for member/team/broadcast; bad act → `422 validation`.
- Two WS clients on team `dawn`: a `send` from Ada to Lin yields a `deliver` to Lin and an `ack` to Ada; Lin offline → message appears in Lin's `inbox` fetch with correct unread count.
- Presence: attach → online in roster; stop heartbeats → reaper offlines within ~`timeout+interval`; clean close → immediate offline.
- Single-active newest-wins (agents, ADR 017): a second concurrent `claim` for the same _agent_ Member takes over and the first receives `superseded`; after detach, a re-attach within the 45s grace succeeds (the `held_until` seat is reclaimed). Kind-scoped (ADR 042): two concurrent claims for the same _human_ Member both occupy (neither superseded), a directed message and a `@team` broadcast both deliver to both human sessions, and the roster lists the human once with both surfaces. Workspace-scoped + durability-gated (ADR 068/092/368): a re-attach whose `workspace` label changed but whose `workspace_key` did not is the SAME workspace (a branch switch must not evict the live session), two distinct keys are two workspaces even under one folder name, and a claim carrying no key falls back to label equality; a same-workspace probe that disconnects within the grace never supersedes the incumbent, while a durable same-workspace successor reaps its predecessor with `same_workspace:true` after `supersedeGraceMs`; a different-workspace claim still supersedes immediately (no `same_workspace` flag). A `wake` claim against a live `session` (or unstamped) occupant is refused `claim_conflict` on both transports, from the same or another workspace, and never reaps it; an attended claim still displaces a wake (ADR 444).
- Activity: a present Member with a recent `status_update` resolves to `working` (with `state`/`last_status_at`); present without one → `idle` (ADR 140); no fresh presence → `offline`. Offline seats also project `offline_reason` (ADR 141).
- Availability (ADR 044): `POST /availability` sets the caller's seat; the roster reflects `away`+`until` / `dnd` / `available`; `until` is kept only for `away`; an unknown status → `400 bad_request`; unauthenticated → `401`.
- `seedDawn` produces the exact fixture in `01-data-model.md`.
- Governed authorization (ADR 411): policy replacement is admin-only and secret-free; launch issuance requires a human issuer and an enrolled node-bound agent Member; the `msla_` token is hash-only and one-shot; consumption rejects expiry/revocation/replay/mismatch and missing or held Presence; authorization rejects revoked nodes, stale Presence, inactive Members, closed/unowned context, and policy/model violations with stable structured reasons; unmanaged Teams remain unchanged while enforcement is `off`.
