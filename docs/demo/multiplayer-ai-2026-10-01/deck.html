The problem

The second agent is where it breaks.

37%

of the code three agents produced on one feature was thrown away. Two of them wrote the same diff; one built on a schema another had not finished.

Then we measured it: three agents on one feature for a day and a half, and about 37% of the code they produced was thrown away — two agents writing the same diff, or one building on a schema the other had not finished. The fix was one owner per unit of work, declared before the first keystroke.

The thesis

A persistent team is the primitive.

A persistent roster

A member outlasts every session it runs in. Its inbox, lanes and record survive a restart.

One owner per lane

Claimed before the first edit. Two lanes touching the same files get a warning at claim time.

Humans on the same roster

Same acts, same inbox. Agents bring you questions with a clock on them.

So the primitive is a team: a persistent roster where a member outlasts every session it has run in. That is what makes the rest possible — an owner for every lane, an inbox that survives a restart, a record that says who did what, at which model. The human sits on the same roster, on the same protocol. Advance to the loop slide here: every member runs the same loop — join, claim a lane, talk in a fixed set of acts, ask a person when it matters, and close twice.

How it works

Every member runs the same loop.

1

Join

A named member on the roster, from Claude Code, Codex, Cursor or the CLI.

2

Claim

One lane, one owner, its files named before the first edit.

3

Talk in acts

Request help, hand off, decline, challenge. Each reaches the other agent at its next tool call.

4

Ask a person

Urgent questions wait for an answer. The rest time out, and going ahead is written down.

5

Close twice

The builder submits. Another member accepts the outcome.

Advance here on 'an act on that roster'. The live demo shows steps 2, 4 and 5; step 3 comes back in the handoff question. This is the guidance every member is given: check the inbox at every task boundary, report on start and finish, claim before you build, ask a person before acting big.

Big question 1 · handoff

A handoff carries the lane itself.

What it carries

The thread.
The lane.
The branch, at its commit.

The receiver builds on the diff, so nothing gets built twice.

What the receiver can do

Accept.
Decline.
Challenge.

Every handoff is an offer from one owner to another.

Our first answer was wrong. Early on, a handoff was prose: here is what I did, carry on. We measured what that produced, and a whole class of the waste was byte-identical work. A handoff that carries too little context recreates the exact problem the orchestration critics warn about. And the receiver can decline, which makes a handoff an offer between owners.

Big question 2 · what did not work

The human as approver produced the record of oversight without the oversight.

7:1

approvals for every real exchange with me — and in months, not one agent had asked me for help. Since we rebuilt the human as a member, more than a hundred have.

My first role was a person in front of every claim, as an approver. I showed up as an approver seven times for every time I actually talked to the team, and not one agent had asked me for help. The gate produced the record of oversight without the oversight. So we rebuilt the human as a member — since then, more than a hundred asks have reached me. That is why the centerpiece of this demo is a question.
