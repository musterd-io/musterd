# 657 — A human's note is sealed to that human's machines

- Status: accepted
- Date: 2026-10-18
- Lane: `01M561YWP0` (goal `security`)
- Design: `docs/design/seat-memory-isolation.md`, "Per-seat encryption, for human seats only"
- Relates to: ADR 093 (seat memory), ADR 200 (credential custody), ADR 358 (a human seat trusts a
  set of machines), ADR 366 (memory replication), ADR 430 (wake packet), ADR 522 (claims checked on
  read), ADR 651 (who reads a note), ADR 654 (who saved it)
- Protocol: adds `SealedNoteSchema`, `NoteRecipientsSchema` and the `./note-seal` subpath. Feature
  epoch 36.

## Context

ADR 651 made a human seat's note readable by that human only. The rule holds at every musterd read
path, but the note is still plain text in places no read rule reaches. Those places are the
daemon's `seat_memory` row and the `continuity.memory_saved` audit row that carries the body
(ADR 366). From there it is copied into the hub's `sync_log` and into every peer that folds it, and
later into Cloud and its backups. nick decided on 2026-10-17 that a human's note is encrypted to
that human's own machines, after lanes 1 to 4 and before launch.

## Problem

Only the human's own machines should be able to turn the stored note back into text. Every other
holder should have only ciphertext: the server, the hub, peers, Cloud and the audit log. Three
things must stay true at the same time:

- The note still follows the human to a second trusted machine (ADR 358, ADR 366).
- Agent notes stay plain text, because the server builds wake packets from them (ADR 430).
- No new dependency is added.

## Decision

1. **Each machine has a note key.** It is an X25519 keypair, generated by Node's built-in `crypto`
   the first time a human seat on that machine needs one. The private half lives in
   `~/.musterd/note-key.json`, mode 0600. `MUSTERD_NOTE_KEY` overrides the path, and otherwise the
   file sits beside `MUSTERD_CONFIG` when that is set. The server receives only the public half,
   which is stored on the machine's node row (`nodes.note_key`, migration v109).
2. **The client seals, and the server refuses plain text from a human.** The CLI and the MCP adapter
   encrypt the headline and body together before `PUT /memory`. The scheme works the way `age` does:
   - A random 32-byte content key encrypts the note with AES-256-GCM.
   - For each recipient, a fresh ephemeral X25519 key is combined with that recipient's public key.
     HKDF-SHA256 turns the result into a key that wraps the content key, again with AES-256-GCM.
   - The sealed body is the string `mssealed1.` followed by base64url JSON
     `{v, to:[{node, pk, epk, wrap}], iv, ct}`. The format and the helpers live in `@musterd/protocol`
     (schema in the main entry; seal and open in the `./note-seal` subpath, which is Node-only).
   - For a human seat, the server accepts a save only when the body is a sealed note **and** the
     headline is the fixed `sealed note`. A plain-text headline could otherwise leak what the body
     hides.
   - For an agent seat, the server refuses a sealed body, which keeps ADR 430's plain-text wake
     packets.
   - The sealed body may be up to 16 KiB. The 8 KiB plain-text cap is enforced by the client, before
     sealing, because the server can no longer measure it.
3. **The recipients are the human's trusted machines.** A human seat calls
   `POST /teams/:slug/memory/recipients {public_key}`. In one call, the server records this
   machine's public key on its node and returns every node in the seat's set (ADR 358) as `{node_id,
   label, public_key | null}`. If nobody has spoken for the seat yet, the set is just this node.
   On an enrolled joiner, the call goes to the hub under the machine credential
   (`POST /teams/:slug/sync/note-recipients {seat, public_key}`). The hub records the key for the
   node that authenticated and answers from its own set, because the set lives there. For an agent
   seat the call answers `{ seal: false }` and records nothing.
4. **Sealed again when a machine is newly trusted.** On every read or save, a machine that can open
   the note compares the note's recipients with the seat's current keyed machines. If a trusted
   machine is missing, the machine re-seals the note to the full set. A machine that is trusted but
   has never registered a key cannot be a recipient yet. The read on that machine registers its key
   and says which machines can open the note: "read it once on one of those". A plain-text note
   saved before this ADR is sealed the first time its human reads or saves it.
5. **What this does not buy, said out loud.**
   - **A removed machine.** It drops out of the next seal. Anything it already received stays
     readable on it.
   - **Losing every machine.** If every key is lost, the note is lost with it. It is working memory
     of at most 8 KiB, so this is acceptable. Old ciphertext in audit rows becomes unreadable along
     with it.
   - **The human's own agents.** On a laptop they run as the human's user, so they can read
     `note-key.json` just as they can read `musterd.db`. The laptop tier's deny rules (lane
     `01M561YQN3`) add the key file to the denied paths. The real barrier is the hosted tier
     (lane `01M561Z0W3`).
   - **History saved before this ADR.** Audit rows written before a human's first sealed save keep
     their plain-text bodies, on this daemon and on every peer that folded them. Nothing here rewrites
     replicated history.

## Alternatives considered

- **Seal on the server with the public keys.** The server would see the plain text on every save,
  and keeping that text away from it is the point.
- **One key per human, copied between machines.** It needs a channel for moving a private key,
  which musterd does not have. Per-machine keys reuse the trust set that ADR 358 already built, the
  same way `age` handles several recipients.
- **Encrypt agent notes too.** Refused in the design (nick, 2026-10-17): every human would become a
  recipient, the wake packet would have to be built on the client, and on a laptop the agent holds
  the key anyway.
- **Keep the real headline in plain text.** The headline is the summary of the body, so it would leak
  most of what sealing hides.

## Consequences

- **Claim checks stop for human notes.** The server can no longer read a human's note, so ADR 522's
  `checks` are empty for one. Agent notes keep them.
- **Old adapters can't save a human's note.** An old CLI or MCP adapter, and the remote MCP surface
  (which runs on the server and holds no machine key), get a refusal that names the fix: save from
  an up-to-date `musterd` on one of your machines.
- **Occupy and orientation read `sealed note`.** The occupied frame, `status` and orientation show
  `sealed note` as the headline for a human seat. `musterd memory` decrypts and shows the real one.

## Observability & Evaluation

- **Traces:** `node.note_key_set` (allow) records each new or changed public key, with its node and
  a fingerprint of the key. A refused plain-text save from a human writes nothing, because the
  refusal is the request's 400.
- **Eval:**
  - `note-seal.test.ts` (protocol) covers the round trip, a wrong key, a tampered stanza, and
    re-sealing to a wider set.
  - The server tests cover the human refusals (plain text, a stray headline), the agent refusal
    (a sealed body), the recipients route on a standalone daemon, and the hub route over the joiner
    forward. The canary (`integration.memory-canary.test.ts`) gains one assertion: a human's
    stored row, its audit row and its envelope never hold the plain-text canary.
  - The CLI tests cover save, then read, then re-sealing on a newly trusted machine.
- **Experiment:** n/a. This is a confidentiality property, so it either holds or it does not, and
  the canary is its falsifier.
